## 1. 问题与目标

当前 Provider、模型名、Base URL 和 API Key 分散在云函数环境变量及多个 service 中，切换模型需要改代码或重新配置函数。二期第一项要将模型选择、Provider 账号和功能路由集中管理，使测试环境可以快速切换并验证，而不改变生产配置。

## 2. 用户故事

- 作为开发者，我希望在后台为不同 AI 功能选择主模型和备用模型，不修改业务代码。
- 作为开发者，我希望新增或停用 Provider Key，但后台不显示完整 Key。
- 作为开发者，我希望测试连接并看到明确的成功、失败、耗时和错误码。
- 作为发布者，我希望一键回滚到上一套已验证配置。
- 作为审计者，我希望知道谁在什么时候切换了哪个功能的模型。

## 3. MVP 范围

首期支持 DeepSeek、Qwen、SenseNova 三个 Provider：

- Provider 账号新增、停用、恢复。
- Base URL、模型 ID、超时、最大 Token、温度配置。
- 按功能配置主模型和备用模型。
- 测试连接。
- 发布配置、查看当前版本、回滚上一版本。
- Key 仅显示末四位和状态，不回显完整值。
- 审计日志。

功能路由至少覆盖：`vision-analysis`、`nutrition-insight`、`coach`。混元和自动负载均衡不纳入 MVP。

## 4. 业务规则

1. 同一功能同一时刻只能有一个主模型；备用模型可为空。
2. Provider 账号停用后，不能被新路由使用，但不影响历史审计记录。
3. 只有已启用且连接测试通过的配置才能发布。
4. 配置发布必须生成递增版本号，并保留上一版本。
5. 运行时读取测试环境配置，不能读取生产环境数据或密钥。
6. 完整 API Key 不进入前端 bundle、数据库明文、日志、审计详情或接口响应。
7. 测试连接不得把用户业务输入写入审计日志。

## 5. EARS 验收标准

- 当管理员打开配置中心时，系统应显示当前环境、当前发布版本和各功能主/备模型。
- 当管理员保存 Provider Key 时，系统应只显示 Provider、末四位和状态，不返回完整 Key。
- 当管理员提交测试连接时，系统应在限定超时时间内显示成功或脱敏失败原因。
- 当管理员发布有效配置时，系统应使新请求使用新版本，并记录审计日志。
- 当管理员回滚时，系统应恢复上一套配置，并记录回滚原因和操作者。
- 当配置无主模型、Provider 已停用或 Key 不可用时，系统不得允许发布。
- 当 Provider 调用失败且存在备用模型时，系统应按路由顺序尝试备用模型，并记录 fallback 状态。
- 当后台页面位于测试 Hosting 域名时，所有请求必须指向测试 API；不得出现生产 API 调用。

## 6. 非目标

- 不做自动按成本/延迟动态负载均衡。
- 不做复杂 RBAC；当前只有一名开发者。
- 不把完整 API Key 存入普通业务表明文。
- 不在本项中改造所有 Prompt、配额策略或 Provider 能力本身。
- 不在本项中修改生产配置或生产数据库。
