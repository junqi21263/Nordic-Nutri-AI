# 分类批量生图与审核流程设计

## 目标与范围

为食物图片审核台增加可靠的批量创建、云端执行和审核重试能力。管理员不再填写食物 ID：每次只选择一个分类，系统从该分类中选择尚无审核主图的食物。

本次范围仅包括主环境的图片批次服务、定时调度函数、审核台和必要的数据库迁移；不改变小程序登录、主数据库环境、食物详情页或远程混元 Worker 的职责。

## 已确认规则

- 每个批次只选择一个食物分类。
- 候选集合为该分类中没有主图、未在其他活动批次中处理的食物。
- 默认 20 条，可在 1--100 条之间调整。
- 每种食物首次只生成 1 张候选图。
- 人工拒绝必须填写原因；原因将注入下一次提示词。
- 单个食物最多尝试 3 次，包含首次生成；到达上限后进入失败待人工处理。
- 启动后的批次由云端调度器执行，后台网页关闭后仍继续运行。

## 管理端交互

审核台保留三栏布局：左侧只展示批次和进度，中间展示候选图队列，右侧为桌面端悬浮的审核面板。

顶部控制台提供以下操作：

1. **创建批次**：弹窗选择一个分类和数量，显示可选数量、将跳过的已有主图数量、预计首轮用量和最大用量；确认后创建 `draft` 批次。
2. **启动 / 暂停 / 继续 / 取消**：仅作用于当前批次。启动后显示“云端执行中”，而不是浏览器自动执行状态。
3. **刷新**：轮询进度和候选图，不承担任务执行。

创建接口由服务端完成筛选并冻结最终 `food_id` 列表。页面不展示或要求粘贴 ID，也不提供 CSV 或跨分类混选入口。

中间队列的筛选项为待审核、生成中、待重试、失败和全部。右侧审核面板展示大图、食品名称和分类、当前尝试次数、最终提示词、生成信息以及通过/拒绝操作。通过后卡片立即显示“已通过”；拒绝后显示“待重试”或“失败待人工处理”。

## 数据与状态

继续使用 `food_image_batches` 和 `food_image_batch_items`，并在批次项中补充以下可追溯数据：

- `last_image_id`：最近一次候选图；
- `retry_reason`：最近一次人工拒绝原因；
- `locked_at`、`locked_by`：调度器领取锁；
- `next_retry_at`：可再次领取的时间；
- `prompt_plan_json`：本次实际使用的提示词计划。

批次状态为 `draft`、`running`、`paused`、`completed`、`completed_with_errors` 和 `cancelled`。批次项状态为 `pending`、`generating`、`needs_review`、`needs_retry`、`completed`、`failed`、`skipped`。

`completed` 只表示审核通过并已设为主图。候选图生成成功但尚未审核时必须为 `needs_review`，不能被统计为完成。

## 服务端接口

保留现有批次详情、状态变更和单步 Worker 接口，并增加或调整以下受管理员会话保护的接口：

- `GET /food-image-batches/selection-preview?categoryId=&count=`：返回该分类可纳入、已有主图、活动批次冲突和将要选择的数量；
- `POST /food-image-batches`：接收 `categoryId`、`count`、批次名称和固定执行参数，在服务端筛选并创建冻结的批次项；
- `POST /food-image-batches/:id/start|pause|resume|cancel`：只变更状态，不让浏览器承担执行循环；
- `POST /food-images/:id/reject`：同时更新候选图和对应批次项；若仍有尝试次数，写入 `retry_reason` 并置为 `needs_retry`，否则置为 `failed`。

筛选顺序必须稳定：按分类内的目录排序、中文展示名、食物 ID 依次排序。服务端创建前会再次验证食物没有主图且没有被活动批次锁定；竞态冲突项记录为 `skipped`，不会重复生图。

## 云端调度器

新增内部定时函数 `food-image-batch-dispatcher`，每分钟触发一次。它使用服务端身份直接调用批次服务，不通过管理员浏览器令牌或公开 HTTP 路由。

一次触发会遍历 `running` 批次，在函数时间预算内循环领取任务；每轮最多按该批次 `concurrency` 并行处理，默认 2、最大 5。领取使用条件更新，只有仍为 `pending` 或 `needs_retry` 的项可从同一状态改为 `generating`。函数中断或超时后，下一个分钟触发从未完成项继续；过期锁会被安全回收。

暂停和取消只阻止后续领取，不中断已经向混元发送的请求。取消会将尚未领取的 `pending` 和 `needs_retry` 项标记为 `skipped`；已有候选图保留审计记录。

## 审核与重试

生成成功后，系统将图片上传主环境 Storage、写入候选图并将批次项转为 `needs_review`。审核通过的单一入口同时：设置图片审核通过、更新 `foods.primary_image_id`、完成图片任务、完成对应批次项并刷新批次汇总。

审核拒绝时，系统保存拒绝原因、候选图的拒绝状态和批次项的重试原因。未达到 3 次时，批次项变为 `needs_retry`；下一次调度会将拒绝原因追加到提示词约束中，例如要求移除错误配菜、修正烹饪状态或主体形态。达到上限时，批次项变为 `failed`，只允许管理员手动复核或创建新批次后再次生成。

## 验证标准

自动测试必须覆盖：

1. 单分类无主图预览和稳定选材；
2. 已有主图和活动批次冲突项的排除；
3. 创建时冻结 food ID 且数量范围为 1--100；
4. 云端调度器的领取锁、并发上限、暂停、取消和中断恢复；
5. 通过动作同步图片、食物、任务和批次项状态；
6. 拒绝原因进入下一次提示词，且第 3 次后停止自动重试；
7. 管理端状态标签和顶部控制台的 DOM 回归测试。

运行验收使用一个真实的 20 条单分类批次：创建、启动、关闭审核页、确认云端继续生成、审核通过一张图、拒绝一张图并验证下一次提示词，以及在小程序中确认通过图成为食物详情页主图。
