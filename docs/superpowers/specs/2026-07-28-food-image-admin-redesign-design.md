# 食物图片管理后台改版设计

## 目标

将现有“批次看板 + 单任务审核”的纵向长页改为面向运营审核的三栏工作台。管理员打开页面后应先看到待审核图片，再快速完成通过或拒绝，而不是阅读大段自动提示词。

本次仅重构本地 `cloudbase/admin/food-images.html` 的界面与前端交互组织；不改动 CloudBase 函数、数据库迁移、图片生成提示词、批次规则和鉴权规则。

## 设计方向

采用“北欧编辑部式运营台”：暖白背景、深松绿主色、雾绿状态面、亚麻色图片底板。标题使用 `Noto Serif SC`，正文使用 `PingFang SC`，作为现有中文产品可读性优先的品牌字体覆盖。

色彩令牌：

- 墨绿：`#173D2A`，主要操作与标题。
- 森林绿：`#2E6046`，成功与进度。
- 雾绿：`#E8EFE7`，次级状态面。
- 亚麻白：`#FAF8F3`，主画布。
- 石墨：`#24312B`，正文。
- 危险红：`#B64A3B`，拒绝与失败，不用于主操作。

## 信息架构

页面固定为以下五个区域：

1. 顶部操作条：产品标识、批次状态、待审核数、刷新与诊断。API Base 和 Bearer Token 收入“连接设置”折叠区，不再占据首屏。
2. 左侧批次轨道：显示批次名称、进度、状态与配额；可创建草稿、启动、暂停、恢复，但已完成批次不显示运行按钮。
3. 中央审核队列：默认只列出 `needs_review` 项，使用 2 列候选图网格；每个条目显示食物名称、分类、生成状态。通过筛选切换到失败、生成中、全部。
4. 右侧审核检查器：选中候选图后显示大图、食物名、分类、简短提示词摘要和生成错误（如果有）；提供“通过并设为主图”与“拒绝并填写原因”。
5. 底部折叠的任务与响应区：保留“手动创建任务”“jobId 加载”“原始响应”，用于排障，不干扰正常审核。

## 审核流程

1. 页面加载批次与统计；默认选中最新的运行中批次，否则选中最新的待审核批次。
2. 选中批次后自动加载全部批次项；只展示有 `jobId` 且状态为 `needs_review` 的项。
3. 点击食物卡片，加载该 job 的候选图；若一项有多张图，显示候选缩略图并让管理员选择。
4. 点击通过：调用既有 `POST /food-images/:imageId/approve`，返回成功后从待审核队列移除，并刷新统计与批次进度。
5. 点击拒绝：要求填写简短原因，调用既有拒绝接口，成功后同样刷新。
6. “查看自动提示词”默认折叠，只作为排障与质量溯源信息，不作为主要内容。

## 状态与异常

- 无待审核：中央区域显示“当前批次已审核完”，并提供切换批次入口。
- 图片加载失败：保留食物名、jobId 与“重新加载”按钮，不自动通过或跳过。
- 请求未授权：在连接设置内提示重新粘贴管理员会话 Token，不在浏览器持久化该 Token。
- 批次失败：左侧标记失败数，中央筛选可进入失败项查看错误码与重新执行下一条入口。

## 响应式与可访问性

- 桌面端（>= 1100px）：三栏布局，中央审核区为主。
- 中等宽度（760–1099px）：左轨道收窄，右检查器移动到中央区下方。
- 窄屏：依次显示批次、候选图、检查器；关键通过/拒绝按钮固定在屏幕底部。
- 所有状态使用文字和颜色双重表达；图片 `alt` 使用食物名；操作按钮应有明确标签。

## 验收标准

- 用户不需要复制 jobId，即可从批次任务直接看到候选图。
- 首屏不再显示完整提示词表格；待审核候选图是视觉主角。
- 可以在一个页面完成选图、通过或拒绝，并即时刷新待审核数量。
- 现有批次管理、单任务加载、诊断与原始响应仍然可用。
- 页面不持久化管理员 Bearer Token，且不改变任何服务端接口。

## 验证方式

- 静态：抽取内联脚本执行 `node --check`，并运行 `git diff --check`。
- 运行时：在本地后台填入当前会话 Token，加载首轮 20 条批次；验证候选图加载、通过、拒绝、计数刷新与空状态。
- 回归：不改动 `get-login-ticket` 函数或前端小程序构建产物。
