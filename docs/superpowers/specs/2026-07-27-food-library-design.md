# 标准食材库 V1：分类、后端与批量图片设计

## 已确认的产品边界

- V1 是独立的**标准食材库**，目标 4,000–5,000 条。
- 面向中文用户的日常健康饮食，同时覆盖常见欧美/北欧食材。
- 家常菜、轻食组合、餐厅菜与食谱属于后续“菜品库”，不进入 V1。
- USDA/Open Food Facts 仅是营养参考或溯源数据；不决定用户名称、分类或是否可发布。
- 主环境 `lewis-healthy-d4glgqqzv73a5bc10` 继续保存目录、审核和图片；`dev-d8g3hqv2b0de38046` 只负责混元生图。

## 数据模型

保留 `foods`、`food_categories`、`food_tags`、`food_images`、`food_image_jobs` 和现有服务器端 RLS。以增量迁移扩展，不删除既有食物 ID 或图片记录。

### `food_categories`

新增/规范：`parent_id`、`level`、`code`、`name_zh`、`name_en`、`icon`、`sort_order`、`is_active`。`code` 不可变；仅二级节点可被 `foods.category_id` 引用。

### `foods`

保留现有每 100g 宏量营养字段与图片引用；新增或规范：

- `canonical_key`：稳定、去语言化的标准食物键，唯一。
- `food_kind`：V1 固定为 `ingredient`，为菜品库预留类型边界。
- `publish_status`：`draft | reviewing | published | quarantined | retired`。
- `food_form`：`raw | cooked | dried | frozen | canned | liquid | powdered | fermented`。
- `default_cooking_method`：仅描述该标准食物默认形态，不等于菜品做法。
- `image_policy`：`generate | licensed | external | none`。
- `image_subject_zh`：生成图必须呈现的主体说明；不接受从名称猜测。
- `catalog_version`：目录导入版本，支持审计与回滚。

`published` 记录必须有中文名、叶子分类、完整的基础营养值、`image_subject_zh` 和 `food_kind=ingredient`。

### 支撑表

- `food_aliases`：`food_id`、`alias`、`normalized_alias`、`language`、`alias_type`。存中文俗名、英文、拼音、繁体和常见误拼。
- `food_reference_sources`：`food_id`、`source`、`source_record_id`、`source_payload_ref`、`nutrition_confidence`。USDA 仅存在于此层。
- `food_catalog_batches`：目录版本、导入摘要、校验结果、创建者、发布状态；批次不合格时不可发布。
- 现有 `food_tags` 继续作为多选筛选维度，例如高蛋白、低脂、高纤维、中式常见、北欧常见、素食。

## 后端边界与接口

所有数据仍通过主环境 HTTP 云函数 `get-login-ticket` 读写，PG 表保持 server-only RLS。

| 接口 | 行为 |
| --- | --- |
| `GET /foods/categories` | 返回活跃分类树、各节点已发布数量和图标 |
| `GET /foods` | 仅返回 `published`；支持关键词、叶子分类、标签、形态筛选和服务端分页 |
| `GET /foods/:id` | 返回标准食物、营养、别名、审核后的主图 |
| `GET /foods/suggestions` | 名称、别名、拼音的轻量搜索建议 |
| 管理端目录接口 | 批次预览、结构校验、重复检测、发布/回退、分类修订 |
| 管理端图片接口 | 仅为符合资格的食物创建生成任务，并按分类/批次查看和审核候选图 |

搜索优先级为：中文标准名 → 中文别名 → 拼音/英文 → `search_keywords`。使用当前名称和分类索引，增加别名规范化索引；所有列表服务端分页（20–40 条）。5,000 条规模不需要独立搜索服务。

## 数据质量与图片资格

目录导入必须在写入前校验：中文名、唯一 `canonical_key`、叶子分类、营养基础、食物形态和图片主体。导入后产生 `draft`，通过批次审核才转为 `published`。

图片任务仅允许以下条件同时成立：

1. `publish_status=published`；
2. `image_policy=generate`；
3. 没有已审核主图；
4. 不是重复 `canonical_key` / 图片实体；
5. 具备 `image_subject_zh` 与适用形态；
6. 所属目录批次已发布。

图片仍沿用 `missing → queued → generating → reviewing → ready/failed`。每食物默认 1 张候选，审核不合格才明确重生；不自动发布。

## 数据迁移与批量节奏

1. 扩展分类树、标准食物字段和别名/批次表。
2. 将当前 51 条 fixture 映射为标准食物的种子数据；已审核鸡胸肉主图保持不动。
3. 将当前 60 条未翻译的原始 USDA 记录标记为 `quarantined`，保留溯源但从搜索、展示和图片队列排除。
4. 以受版本控制的目录文件导入 4,000–5,000 条标准食物，先做校验和管理员预览，再分批发布。
5. 以分类为单位创建图片任务：每批 100–300 条、默认 1 张候选；根据人工审核吞吐量调整每日上限。

## 非目标与验收边界

- 不在 V1 收录组合菜、食谱或餐厅菜。
- 不按 USDA 原始分类展示食物，也不将未清洗来源记录直接生图。
- 不自动批准 AI 图；只有审核后的主图可以公开展示。
- 不改变登录、小程序身份、主数据库环境或跨环境 HMAC Worker 边界。

验收时，目录中每个已发布食物均可按中文名/别名找到，具有叶子分类与可信营养基础；待生成队列不包含未发布或隔离数据；图片审核后可在小程序稳定展示。
