# 资料与目标数据补全设计

## 目标

让现有小程序页面中已展示、可编辑的用户资料真实保存到 CloudBase PostgreSQL，并在下一次登录时由服务端读取回填。保持现有页面层级、视觉样式和登录链路不变。

## 范围

1. onboarding 增加昵称字段，作为首次资料录入的一部分；昵称必填。目标体重继续由既有「调整目标」页维护，以保持身体资料页视觉冻结。
2. 编辑资料页保存昵称、当前体重及目标方向：昵称写入 `profiles`，体重以新的当前版本写入 `body_profiles`，方向保留当前目标中的体重/热量后写入新的 `user_goals` 版本。
3. 调整目标页保存目标体重与每日目标热量，写入新的当前 `user_goals` 版本。
4. 已登录用户启动时读取当前 profile、body profile 与 goal；数据库字段为空时前端不伪造或回写演示默认值。

## 服务端边界

- 所有写操作继续调用现有 HTTPS 云函数。
- 服务端从 HMAC 产品 session 解析用户 ID；不接受客户端 `userId`。
- 体重和目标采用版本化写入：旧记录 `is_current=false`，新记录 `is_current=true`。
- `saveOnboarding` 在完成引导时同时写入昵称，确保首次账号读取不再缺少昵称。

## 前端交互

- onboarding 在现有身体资料步骤内补充昵称输入与校验，不新增页面；目标体重由既有目标调整页保存。
- 编辑资料的保存按钮将三项变更并行/顺序提交；任一失败时保留当前页面并提示失败，不把局部成功误显示成全部成功。
- 调整目标继续沿用当前保存反馈。
- 完成保存后更新 Zustand profile store，以便页面即时反映服务器确认后的值。

## 异常与兼容性

- 旧用户已有空昵称/目标体重时，读取结果可为 `null`；只有用户主动保存对应表单才会写入。
- 不使用页面中的演示默认昵称或体重作为数据库回填值。
- 不修改页面视觉风格、底部导航、登录方式或 Supabase 隔离边界。

## 验收

1. 完成 onboarding 后，`account` 返回输入的昵称；完成既有目标调整后，返回保存的目标体重。
2. 编辑资料后，重新登录仍可读取新昵称、体重与目标方向。
3. 调整目标后，重新登录仍可读取目标体重和热量。
4. 单元测试、类型检查、微信小程序构建和 WXSS 检查通过。
