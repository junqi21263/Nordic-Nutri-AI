# USDA 食物库设计

## 目标

为 Nordic Nutri AI 增加服务端驱动的标准食物搜索能力。小程序只请求本项目的既有 HTTPS 接口；USDA FoodData Central 密钥始终只保留在 CloudBase 云函数环境变量中。

## 数据与缓存

- 主数据源：USDA FoodData Central Search API。
- 缓存表：`public.food_catalog`，按 `source + source_food_id` 唯一。
- 缓存范围：名称、品牌、类别、每 100g 的热量/蛋白质/碳水/脂肪、来源、最后同步时间；不保存原始 API 大响应。
- 缓存策略：优先从本地命中；未命中时查询 USDA，并将前 20 条结果写回缓存。缓存有效期为 30 天，过期条目在下次命中时刷新。
- 权限：表仅由既有云函数服务角色访问；客户端无 PG 直连权限。

## 图片策略

USDA 不提供可用于产品展示的官方食物图片。因此首期不把图片二进制写入 PostgreSQL，也不批量抓取第三方原图。界面使用现有食品类别视觉作为稳定兜底。

后续如接入 Open Food Facts，只保存可追溯的来源、图片 URL 和经过尺寸限制的缓存缩略图；页面必须显示来源和许可证信息。这样既避免了数据库 BLOB 膨胀，也避免小程序首次加载大量图片。

## API

- `GET /foods?query=<关键词>&page=<页码>`：返回最多 20 条 USDA/缓存标准食物。
- `GET /foods/<id>`：返回单个已缓存食物的完整营养值。

所有接口都要求当前产品 session，且对关键词、页码和结果条数执行服务器校验。

## UI 与流程

本次不重做扫描页。新增可从手动记录进入的食物搜索页：搜索后选中一项，回填名称及每 100g 营养值到现有餐食录入流程。沿用当前米白背景、深绿色主操作、PingFang 字体和 `NordicIcon` 图标体系。

## 验证

1. 单元测试覆盖关键词校验、USDA 映射、缓存优先、上游失败和路由鉴权。
2. CloudBase PG 迁移后回读表结构、唯一索引和 RLS。
3. 构建、类型检查、lint、微信小程序校验全部通过。
4. 发布既有 `get-login-ticket` 函数后检查状态为 Active/Available，并用受保护请求验证食物搜索。
