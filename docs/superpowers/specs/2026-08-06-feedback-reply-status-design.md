# 用户反馈处理与后台回复设计

## 目标

让用户能够在「我的 → 反馈与帮助」中查看自己提交的反馈、当前处理状态和后台回复；当存在尚未查看的回复时，以低干扰的小铃铛提醒。后台以中文显示状态，并提供独立的「回复反馈」操作完成处理闭环。

## 范围

### 用户端

1. 保留「反馈与帮助」入口和当前的底部抽屉，不新增独立页面。
2. 抽屉顶部增加下拉切换：`提交反馈` 与 `反馈处理`；默认保持在「提交反馈」。
3. 「反馈处理」仅展示当前登录用户的反馈卡片，每张卡片按时间倒序包含：
   - 分类、提交时间和中文状态；
   - 「你的反馈」中的原始内容；
   - 存在后台回复时显示「我们的回复」、回复内容和回复时间。
4. 个人中心的「反馈与帮助」入口在存在未读后台回复时，在右侧箭头前显示小铃铛；没有未读回复时不显示任何额外标记。
5. 用户进入「反馈处理」后，将本次列表中已回复且未读的反馈标为已读，并刷新入口提醒。提交反馈不会自动消除既有未读回复。

### 后台

1. 反馈状态的展示文字统一为中文，但 API 和数据库继续使用现有英文枚举：
   - `new`：已收到
   - `reviewing`：处理中
   - `resolved`：已回复
   - `closed`：已关闭
2. 反馈表新增「操作」列，其中每条反馈提供「回复反馈」按钮。
3. 点击后打开轻量弹窗，展示用户、分类、提交时间、原始反馈、当前状态和已有回复；管理员可：
   - 单独更新处理状态；
   - 填写或修改回复；
   - 通过「保存回复并通知用户」保存回复、记录时间，并自动设为 `resolved`（已回复）。
4. 回复为空时不能执行「保存回复并通知用户」；仅更新状态不会产生用户提醒。

## 数据与 API

反馈记录新增：

- `admin_reply text null`：后台对用户可见的回复；
- `replied_at timestamptz null`：最近一次后台回复时间；
- `reply_read_at timestamptz null`：用户最近一次查看该回复的时间。

约束：回复最多 2,000 字符；回复、已读时间均由服务端在鉴权后写入。后台操作需要管理员会话；用户端所有列表、未读统计与已读写入均从产品会话的用户 ID 推导，不能接收任意用户 ID。

新增或扩展接口：

- 管理员 `PATCH /api/admin/feedback/:id`：接受状态或回复；有有效回复时更新 `admin_reply`、`replied_at`，并将状态置为 `resolved`。
- 用户 `GET /feedback/mine`：返回当前用户的反馈列表、中文展示所需原始状态和未读回复数量。
- 用户 `POST /feedback/read`：只接收当前列表内自己的已回复反馈 ID，批量写入 `reply_read_at`。

## 状态与提醒规则

```text
已收到 → 处理中 → 已回复 → 已关闭
                     ↓
                用户查看回复
                     ↓
              清除该条未读标记
```

- 铃铛依据 `admin_reply is not null and reply_read_at is null` 的数量决定，和单纯的状态变更无关。
- 管理员重新编辑并保存一条已有回复时，应更新 `replied_at` 并清空 `reply_read_at`，使用户再次收到提醒。
- `closed` 只是运营状态；如该条已有未读回复，仍保留铃铛，直到用户实际查看。

## 非目标

- 不做用户与管理员之间的实时多轮聊天。
- 不引入微信订阅消息、系统推送或站内通知中心。
- 不允许用户编辑已提交反馈；后续补充信息继续以新反馈提交。
- 不改变反馈内容安全校验、管理员登录边界或其他后台模块。

## 验收

1. 后台筛选和状态下拉仅显示中文，保存后仍向 API 提交既有英文状态值。
2. 管理员能从「回复反馈」操作查看上下文、保存回复并自动将状态变为「已回复」。
3. 用户只能读取自己的反馈及回复；无回复时不出现「我们的回复」。
4. 有未读回复时个人中心显示铃铛；打开「反馈处理」后铃铛消失，刷新后仍保持已读。
5. 管理员再次保存回复后，用户会再次看到铃铛。
6. 迁移、函数单元测试、小程序单元测试、TypeScript、Lint 和小程序构建通过。
